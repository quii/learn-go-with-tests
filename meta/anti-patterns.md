# TDD のアンチパターン

ときどき自分の TDD のテクニックを見直し、避けるべき振る舞いを思い出すことが必要です。

TDD のプロセスは概念的には簡単に従えるものですが、実践していくと、自分の設計スキルが試されていることに気づくでしょう。**これを TDD が難しいと勘違いしないでください。難しいのは設計なのです！**

この章では、TDD とテストのアンチパターンをいくつか挙げ、それらをどう改善するかを説明します。

## そもそも TDD をしていない

もちろん、TDD なしでも優れたソフトウェアを書くことは可能です。しかし、私がこれまで見てきたコードの設計やテストの品質に関する問題の多くは、規律ある TDD のアプローチを使っていれば、まず起こり得なかったものです。

TDD の強みの1つは、問題を分解し、何を達成しようとしているのかを理解し（レッド）、それを実現し（グリーン）、そしてそれを正しくする方法をじっくり考える（ブルー/リファクタリング）ための、形式的なプロセスを与えてくれることです。

これがないと、プロセスは場当たり的で緩いものになりがちで、エンジニアリングが本来 _そうであり得る_ よりも難しく _なってしまう可能性があります_ 。

## リファクタリングのステップの制約を誤解している

私はこれまで、いくつものワークショップやモブプログラミング、ペアプログラミングのセッションで、誰かがテストを成功させてリファクタリングの段階に入る場面に立ち会ってきました。少し考えた後、その人が一部のコードを新しい構造体に抽象化するのが良さそうだと考えると、駆け出しの杓子定規な人がこう叫ぶのです。

> そんなことをしてはいけません！ まずそのためのテストを書くべきです。TDD をやっているんですよ！

これはよくある誤解のようです。**テストがグリーンのときは、コードに対して好きなことをしてかまいません**。唯一やってはいけないのは、**振る舞いを追加したり変更したりすること** です。

これらのテストの目的は、_リファクタリングする自由_ を与え、正しい抽象化を見つけ、コードを変更しやすく理解しやすいものにすることです。

## 失敗しないテストがある（あるいは、常緑テスト）

これが驚くほど頻繁に起こります。テストのデバッグや変更を始めて、気づくのです。このテストが失敗するシナリオは存在しない、と。あるいは少なくとも、そのテストが守る _はずの_ 形では失敗しない、と。

**最初のステップ** に従っていれば、TDD でこれが起こることは _ほぼ不可能_ です。

> テストを書き、それが失敗するのを確認する

これはほとんどの場合、開発者がコードを書いた _後で_ テストを書いたり、役に立つテストスイートを作ることよりもテストカバレッジを追いかけたりしたときに起こります。

## 役に立たないアサーション

システムで作業していてテストを壊してしまい、こんなメッセージを見たことはありませんか？

> `false was not equal to true`

false が true と等しくないことは分かっています。これは役に立つメッセージではありません。私が何を壊したのかを教えてくれないからです。これは、TDD のプロセスに従わず、失敗時のエラーメッセージを読んでいないことの兆候です。

原点に立ち返りましょう。

> テストを書き、それが失敗するのを確認する（そしてエラーメッセージを恥じないこと）

## 関係のない詳細をアサートしている

その一例は、実際にはテストで気にしているのがフィールドの1つの値だけなのに、複雑なオブジェクト全体に対してアサーションを行うことです。

```go
// not this, now your test is tightly coupled to the whole object
if !cmp.Equal(complexObject, want) {
	t.Error("got %+v, want %+v", complexObject, want)
}

// be specific, and loosen the coupling
got := complexObject.fieldYouCareAboutForThisTest
if got != want {
	t.Error("got %q, want %q", got, want)
}
```

余計なアサーションは、ドキュメントとしてのテストに「ノイズ」を生み出して読みにくくするだけでなく、テストを、そのテストが気にしていないデータと不必要に結合させてしまいます。つまり、オブジェクトのフィールドやその振る舞いを変更すると、テストで予期しないコンパイルエラーや失敗が起こるかもしれないということです。

これは、レッドの段階に十分厳密に従っていないことの一例です。

- **望ましい振る舞いについて考える代わりに**、既存の設計にテストの書き方を左右させている
- 失敗したテストのエラーメッセージについて十分に検討していない

## ユニットテストの1つのシナリオの中に多くのアサーションがある

多くのアサーションがあると、テストは読みにくくなり、失敗したときのデバッグも難しくなります。

それらは多くの場合、少しずつ忍び込んできます。特にテストのセットアップが複雑な場合、別のことをアサートするために同じひどいセットアップを繰り返すのが億劫になるからです。そうする代わりに、新しいことをアサートしにくくしている設計上の問題を修正すべきです。

役に立つ経験則は、1つのテストにつき1つのアサーションを目指すことです。Go では、必要な場合にはサブテストを活用して、アサーション同士をはっきりと区切りましょう。これは、振る舞いに対するアサーションと実装の詳細に対するアサーションを分けるための便利なテクニックでもあります。

セットアップや実行時間が制約となるその他のテスト（たとえば、Web ブラウザを操作する受け入れテスト）では、少しデバッグしにくいテストになることと、テストの実行時間との間で、メリットとデメリットを比較検討する必要があります。

## テストの声に耳を傾けていない

[Dave Farley は動画「When TDD goes wrong」](https://www.youtube.com/watch?v=UWtEVKVPBQ0&feature=youtu.be)の中でこう指摘しています。

> TDD は、設計に対して可能な限り最速のフィードバックを与えてくれる

私自身の経験から言うと、多くの開発者が TDD を実践しようとしているものの、TDD のプロセスから返ってくるシグナルを頻繁に無視しています。そのため、彼らは依然として、貧弱なテストスイートを抱えた、壊れやすく厄介なシステムから抜け出せずにいます。

簡単に言えば、コードをテストするのが難しいなら、コードを _使う_ のも難しいということです。テストをコードの最初のユーザーとして扱えば、そのコードが扱いやすいかどうかが分かるでしょう。

本書ではこのことを何度も強調してきましたが、もう一度言います。**テストの声に耳を傾けましょう**。

### 過剰なセットアップ、多すぎるテストダブルなど

テストで何か興味深いことが起こる前に、20行、50行、100行、200行ものセットアップコードがあるテストを見たことはありませんか？ そしてコードを変更しなければならなくなってその混乱を再び訪れ、別の職業に就いていればよかったと思ったことはありませんか？

ここでのシグナルは何でしょうか？ _耳を傾けてください_。複雑なテスト `==` 複雑なコードです。なぜあなたのコードは複雑なのでしょうか？ そうである必要があるのでしょうか？

- テストに多くのテストダブルがあるということは、テスト対象のコードに多くの依存関係があるということであり、つまり設計に手を入れる必要があるということです。
- テストがモックとのさまざまなやり取りのセットアップに依存しているなら、それはコードが依存先と多くのやり取りをしているということです。それらのやり取りをもっとシンプルにできないか自問してみましょう。

#### 漏れのあるインターフェース

多くのメソッドを持つ `interface` を宣言しているなら、それは抽象化が漏れていることを示しています。その協調関係を、より集約されたメソッドの集合、理想的には1つのメソッドで定義できないか考えてみましょう。

#### インターフェース汚染

Go のことわざにあるように、*インターフェースが大きくなるほど、抽象化は弱くなります（the bigger the interface, the weaker the abstraction）*。パッケージのユーザーに巨大なインターフェースを公開すると、ユーザーはテストの中で API 全体に合致するスタブやモックを作らなければならなくなり、使いもしないメソッドの実装まで用意することになります（場合によっては、使うべきでないことを明示するために単にパニックさせることもあります）。この状況は [インターフェース汚染（interface pollution）](https://rakyll.org/interface-pollution/) として知られるアンチパターンであり、これこそが、標準ライブラリがごく小さなインターフェースしか提供していない理由です。

代わりに、パッケージからは関連するすべてのメソッドをエクスポートした素の構造体を公開し、API のクライアントが、必要なメソッドのサブセットを抽象化する独自のインターフェースを自由に宣言できるようにすべきです。たとえば [go-redis](https://github.com/redis/go-redis) は、API のクライアントに構造体（`redis.Client`）を公開しています。

一般的に言って、クライアントにインターフェースを公開すべきなのは、次の場合だけです。
- インターフェースが、小さく一貫性のある関数の集合で構成されている場合。
- インターフェースとその実装を分離する必要がある場合（たとえば、ユーザーが複数の実装から選択できる場合や、外部の依存関係をモックする必要がある場合）。

#### 使用するテストダブルの種類について考える

- モックは役に立つこともありますが、非常に強力であるがゆえに誤用しやすいものです。代わりにスタブを使うという制約を自分に課してみましょう。
- スパイで実装の詳細を検証することは役に立つこともありますが、避けるようにしましょう。実装の詳細は通常重要ではなく、可能であればテストをそれに結合させたくないことを忘れないでください。テストは **付随的な詳細ではなく、有用な振る舞い** に結合させるようにしましょう。
- テストダブルの分類がよく分からない場合は、[テストダブルの命名に関する私の投稿を読んでください](https://quii.dev/Start_naming_your_test_doubles_correctly)

#### 依存関係を集約する

以下は、Web サイトへの新規ユーザー登録を処理する `http.HandlerFunc` のコードです。

```go
type User struct {
	// Some user fields
}

type UserStore interface {
	CheckEmailExists(email string) (bool, error)
	StoreUser(newUser User) error
}

type Emailer interface {
	SendEmail(to User, body string, subject string) error
}

func NewRegistrationHandler(userStore UserStore, emailer Emailer) http.HandlerFunc {
	return func(writer http.ResponseWriter, request *http.Request) {
		// extract out the user from the request body (handle error)
		// check user exists (handle duplicates, errors)
		// store user (handle errors)
		// compose and send confirmation email (handle error)
		// if we got this far, return 2xx response
	}
}
```

一見すると、この設計はそれほど悪くないと言うのも無理はありません。依存関係は2つしかないのですから！

ハンドラーの責務を考えて、設計を再評価してみましょう。

- リクエストボディを `User` にパースする :white_check_mark:
- `UserStore` を使ってユーザーが存在するかを確認する :question:
- `UserStore` を使ってユーザーを保存する :question:
- メールを作成する :question:
- `Emailer` を使ってメールを送信する :question:
- 成功やエラーなどに応じて、適切な HTTP レスポンスを返す :white_check_mark:

このコードを動かして確かめるには、テストダブルのセットアップやスパイなどの度合いがさまざまに異なる、多くのテストを書かなければならないでしょう。

- 要件が拡大したらどうなるでしょうか？ メールの翻訳は？ SMS での確認も送信するとしたら？ この変更に対応するために HTTP ハンドラーを変更しなければならないことは、あなたにとって理にかなっているでしょうか？
- 「メールを送信すべきである」という重要なルールが HTTP ハンドラーの中にあるのは、正しいと感じられるでしょうか？
    - そのルールを検証するために、なぜ HTTP リクエストを作成してレスポンスを読むという儀式を経なければならないのでしょうか？

**テストの声に耳を傾けましょう**。このコードに対して TDD のやり方でテストを書けば、すぐに居心地の悪さを感じるはずです（少なくとも、あなたの中の怠け者の開発者がいら立つはずです）。苦痛を感じたら、立ち止まって考えましょう。

代わりに設計が次のようだったらどうでしょうか？

```go
type UserService interface {
	Register(newUser User) error
}

func NewRegistrationHandler(userService UserService) http.HandlerFunc {
	return func(writer http.ResponseWriter, request *http.Request) {
		// parse user
		// register user
		// check error, send response
	}
}
```

- ハンドラーのテストがシンプル ✅
- 登録に関するルールの変更は HTTP から切り離されているので、それらのテストもシンプル ✅

## カプセル化を破っている

カプセル化は非常に重要です。パッケージ内のすべてをエクスポート（あるいはパブリックに）しないのには理由があります。密結合を避けるために、表面積の小さい、一貫性のある API が欲しいのです。

何かをテストするために、関数やメソッドをパブリックにしたくなることがあります。そうすると設計が悪くなり、コードの保守者や利用者に紛らわしいメッセージを送ることになります。

その結果として、開発者がテストをデバッグしようとして、最終的にテスト対象の関数が _テストからしか呼び出されていない_ ことに気づく、ということが起こり得ます。これは明らかに **ひどい結果であり、時間の無駄** です。

Go では、テストを書く際のデフォルトの立場を、_パッケージの利用者の視点から_ と考えましょう。テストを `package gocoin_test` のようなテストパッケージに置くことで、これをコンパイル時の制約にできます。そうすれば、パッケージのエクスポートされたメンバーにしかアクセスできなくなるため、実装の詳細に結合してしまうことはあり得なくなります。

## 複雑なテーブルテスト

テーブルテストは、テストのセットアップが同じで入力だけを変えたい場合に、さまざまなシナリオを実行するための優れた方法です。

_しかし_、1つの輝かしいテーブルを持つという名目で、他の種類のテストを無理やり押し込もうとすると、読みにくく理解しにくいものになりかねません。

```go
cases := []struct {
	X                int
	Y                int
	Z                int
	err              error
	IsFullMoon       bool
	IsLeapYear       bool
	AtWarWithEurasia bool
}{}
```

テーブルの `struct` に新しいフィールドやブール値を追加するのではなく、**恐れずにテーブルから抜け出して新しいテストを書きましょう**。

ソフトウェアを書くときに心に留めておくべきことは、

> [シンプルは簡単ではない（Simple is not easy）](https://www.infoq.com/presentations/Simple-Made-Easy/)

ということです。テーブルにフィールドを追加する「だけ」なら簡単かもしれませんが、それによって物事はシンプルとはほど遠いものになりかねません。

## まとめ

ユニットテストに関する問題のほとんどは、通常、次のことに起因しています。

- 開発者が TDD のプロセスに従っていない
- 設計が貧弱である

ですから、優れたソフトウェア設計について学びましょう！

良いニュースは、TDD が _設計スキルを向上させる_ 助けになるということです。冒頭で述べたように、

**TDD の主な目的は、設計に対するフィードバックを提供することです。** 何度でも言いますが、テストの声に耳を傾けましょう。テストはあなたの設計を映し出しているのです。

テストが与えてくれるフィードバックに耳を傾けて、テストの品質について正直になれば、あなたはより良い開発者になれるでしょう。
