# リファクタリングのステップ、最初のチェックリスト

リファクタリングは、十分に練習を積めば、たいていの場合は自然と、それなりに楽にこなせるようになるスキルです。

この活動は、より大きな設計変更と混同されがちですが、両者は別物です。リファクタリングとその他のプログラミング活動を区別しておくと、明確さと規律を持って作業できるので役に立ちます。

## リファクタリングとその他の活動

リファクタリングとは、単に既存のコードを改善することであり、<u>振る舞いは変えません</u>。したがって、テストを変更する必要はないはずです。

これが、リファクタリングがTDDサイクルの3番目のステップである理由です。振る舞いと、それを裏付けるテストを追加したら、リファクタリングはテストコードを一切変更する必要のない活動であるべきです。コードを「リファクタリング」していて、同時にテストも変更しなければならないなら、**あなたは別のことをしています**。

非常に役立つリファクタリングの多くは、覚えるのが簡単で、実行するのも容易です（多くはIDEがほぼ完全に自動化してくれます）。しかし時間が経つにつれて、システムの品質に非常に大きな影響を与えるようになります。

### 「大きな」設計などのその他の活動

> つまり、「本当の」振る舞いは変えていないけれど、テストは変更しなければならない？それは何なの？

ある型に取り組んでいて、そのコードの品質を改善したいとしましょう。*リファクタリングではテストを変更する必要がないはず*なので、次のことはできません。

- 振る舞いを変更する
- メソッドのシグネチャを変更する

…テストはこの2つに結合しているからです。しかし、次のことはできます。

- プライベートなメソッドやフィールド、さらには新しい型やインターフェースを導入する
- パブリックなメソッドの内部を変更する

メソッドのシグネチャを変更したい場合はどうでしょうか？

```go
func (b BirthdayGreeter) WishHappyBirthday(age int, firstname, lastname string, email Email) {
	// some fascinating emailing code
}
```

引数リストが長すぎると感じて、コードにもっと凝集性と意味を持たせたいと思うかもしれません。

```go
func (b BirthdayGreeter) WishHappyBirthday(person Person)
```

さて、あなたは今**設計**をしているので、慎重に進めなければなりません。規律を持ってこれを行わないと、コードも、その背後にあるテストも、*そして*おそらくそれに依存しているものも、めちゃくちゃにしてしまう可能性があります。`WishHappyBirthday`を使っているのはテストだけではないことを忘れないでください。願わくば「本物の」コードでも使われているはずです！

**この変更も、テストファーストで駆動できるはずです**。これが「振る舞い」の変更かどうかについて細かい議論をすることはできますが、あなたはメソッドに異なる振る舞いをさせたいのです。

これは振る舞いの変更なので、ここでもTDDのプロセスを適用しましょう。TDDの利点の1つは、システムの振る舞いの変更を駆動するためのシンプルで安全で再現可能な方法を与えてくれることです。*感覚的に*違うというだけで、こうした状況でそれを放棄する理由があるでしょうか？

この場合、既存のテストを新しい型を使うように変更します。リスクを減らし、規律と明確さをもたらすために、TDDで普段行っている反復的で小さなステップは、こうした状況でも役立ちます。

`WishHappyBirthday`を呼び出すテストはおそらく複数あるでしょう。このようなシナリオでは、テストを1つだけ残して他をすべてコメントアウトし、変更を駆動し、その後で残りのテストを適宜対応していくことをお勧めします。

### 大きな設計

設計には、より大きな変更やより広範な議論が必要になることがあり、通常はある程度の主観性を伴います。システムの一部の設計を変更することは、通常リファクタリングよりも長いプロセスになります。それでもなお、どうすれば小さなステップで行えるかを考えることで、リスクを減らすよう努めるべきです。

### 木を見て森を見ず

> [イギリス英語で「**can't see the wood for the trees**」（アメリカ英語では「can't see the forest for the trees」）と言われる人は、何かの細部に深く入り込みすぎていて、全体として何が重要なのかに気づいていません。](https://www.collinsdictionary.com/dictionary/english/cant-see-the-wood-for-the-trees)

「大きな」設計の問題について話し合うのは、**根底にあるコードがよく整理されている（well-factored）**ときのほうが容易です。あなたや同僚がファイルを開くたびに、散らかったコードを頭の中で解読するのに多大な時間を費やさなければならないとしたら、コードの設計について考える余裕などあるでしょうか？

だからこそ、**TDDのプロセスにおいて絶え間ないリファクタリングがとても重要**なのです。小さな設計上の問題に対処できなければ、より大きなシステムの全体的な設計を組み立てるのは難しくなります。

残念ながら、うまく整理されていないコードは、エンジニアが不安定な土台の上に複雑さを積み重ねていくにつれて、指数関数的に悪化していきます。

## 最初の頭の中のチェックリスト

**TDDサイクルのたびに、頭の中のチェックリストを確認する習慣をつけましょう。** 自分に練習を課せば課すほど、簡単になっていきます。**これは練習が必要なスキルです。** これらの変更はどれも、テストの変更を必要としないはずであることを忘れないでください。

私や同僚が使っているIntelliJ/GoLandのショートカットも載せておきます。新しいエンジニアをコーチするときはいつも、これらのツールを使って素早く安全にリファクタリングする操作を体で覚え、習慣にするよう勧めています。

### 変数のインライン化

変数を作成したものの、それを別のメソッドや関数に渡すだけの場合:

```go
url := baseURL + "/user/" + id
res, err := client.Get(url)
```

変数名が大きな意味を付け加えている場合を*除いて*、インライン化（`command+option+n`）を検討しましょう。

```go
res, err := client.Get(baseURL + "/user/" + id)
```

インライン化を _やりすぎ_ ないようにしましょう。変数をゼロにした結果、誰も読めないばかげたワンライナーができあがるのでは本末転倒です。値に意味のある名前を付けられるなら、そのままにしておくのが一番かもしれません。

### 変数の抽出で値をDRYにする

「同じことを繰り返すな（Don't repeat yourself）」（DRY）。関数の中で同じ値を何度も使っていませんか？ それを抽出し、意味のある名前の変数にすることを検討しましょう（`command+option+v`）。

これは読みやすさの向上に役立ち、同じ値の複数の出現箇所をすべて更新することを覚えておく必要がなくなるので、将来値を変更するのも簡単になります。

### 全般的にDRYにする

[DRY](https://en.wikipedia.org/wiki/Don%27t_repeat_yourself)は最近評判が悪く、それにはある程度の正当な理由があります。DRYは、表面的なレベルで理解するのが*あまりにも*簡単で、その結果誤って適用されてしまう概念の1つです。

エンジニアはDRYを簡単にやりすぎてしまい、DRYの*本当の*考え方である _アイデア_ を1か所にまとめることではなく、数行のコードを節約するために、不可解で絡み合った抽象化を作り出してしまいます。コードの行数が減ることはしばしばDRYの副作用ですが、**それは本当の目標ではありません**。

ですから、確かにDRYは誤って適用されることがありますが、何であれDRYにすることを拒むという正反対の極端もまた悪です。繰り返されたコードはノイズを増やし、保守コストを増大させます。DRYの誤用を恐れて、関連する概念や値を1つにまとめることを拒むのは、*別の*問題を引き起こします。

ですから、「すべてをDRYにしなければならない」か「DRYは悪だ」かのどちらかの極端に走るのではなく、頭を使って、目の前のコードについて考えましょう。何が繰り返されていますか？ それは必要ですか？ 繰り返されたコードをメソッドにカプセル化したら、引数リストは妥当に見えますか？ それは自己文書化されていて、「アイデア」を明確にカプセル化していると感じられますか？

10回中9回は、関数の引数リストを見て、それが散らかっていてわかりにくければ、DRYの適用が下手である可能性が高いです。

あるコードをDRYにするのが難しいと感じるなら、おそらく物事をより複雑にしています。やめることを検討しましょう。

注意してDRYにしましょう。**しかし、これを頻繁に練習することで判断力が向上します**。私は同僚に「とにかく試してみて」と勧め、間違っていたらソース管理を使って安全な状態に戻るようにしています。

<u>**これらを試すことは、議論することよりも多くのことを教えてくれます**</u>。そして、ソース管理と優れた自動テストを組み合わせれば、実験して学ぶための完璧な環境が手に入ります。

### 「マジック」値を抽出する

> [意味が説明されていない、または複数回出現する一意な値で、（できれば）名前付き定数に置き換えられるもの](https://en.wikipedia.org/wiki/Magic_number_(programming))

変数の抽出（command+option+v）や定数の抽出（command+option+c）を使って、マジック値に意味を与えましょう。これはインライン化のリファクタリングの逆と見なすことができます。私はよく、インライン化と抽出を使ってコードを「行ったり来たり」させて、どちらが読みやすいと思うかを判断しています。

繰り返される値を抽出すると、ある種の _結合_ も追加されることを忘れないでください。その値を使うものはすべて、結合されることになります。次のコードを考えてみましょう。

```go
func main() {
	api1Client := http.Client{
		Timeout: 1 * time.Second,
	}
	api2Client := http.Client{
		Timeout: 1 * time.Second,
	}
	api3Client := http.Client{
		Timeout: 1 * time.Second,
	}
	//etc
}
```

アプリケーションのためにいくつかのHTTPクライアントをセットアップしています。ここにはいくつかの _マジック値_ があり、変数を抽出して意味のある名前を付けることで、`Timeout`をDRYにできます。

![A screenshot of me extracting variable](https://i.imgur.com/4sgUG7L.png)

すると、コードは次のようになります。

```go
func main() {
	timeout := 1 * time.Second
	api1Client := http.Client{
		Timeout: timeout,
	}
	api2Client := http.Client{
		Timeout: timeout,
	}
	api3Client := http.Client{
		Timeout: timeout,
	}
	// etc..
}
```

マジック値はなくなり、意味のある名前が付きましたが、同時に3つのクライアントすべてが**同じタイムアウトを共有する**ようにもなりました。それが望んでいることである _かもしれません_。リファクタリングはかなり状況に依存するものですが、注意すべき点です。

IDEをうまく使えれば、_インライン化_ のリファクタリングを行って、クライアントがそれぞれ別の`Timeout`値を持つように戻すことができます。

### パブリックなメソッドや関数をざっと読めるようにする

コードに、過度に長いパブリックなメソッドや関数はありませんか？

メソッドの抽出（`command+option+m`）のリファクタリングを使って、手順をプライベートなメソッドや関数にカプセル化しましょう。

以下のコードには、HTTPリクエストで`POST`できるように、JSON文字列を作成してそれを`io.Reader`に変換するという、退屈で気が散る儀式的な処理があります。

```go
func (ws *WidgetService) CreateWidget(name string) error {
	url := ws.baseURL + "/widgets"
	payload := []byte(`{"name": "` + name + `"}`)

	req, err := http.NewRequest(
		http.MethodPost,
		url,
		bytes.NewBuffer(payload),
	)
	//todo: handle codes, err etc
}
```

まず、変数のインライン化のリファクタリング（command+option+n）を使って、`payload`をバッファの作成部分に入れます。

```go
func (ws *WidgetService) CreateWidget(name string) error {
	url := ws.baseURL + "/widgets"
	req, err := http.NewRequest(
		http.MethodPost,
		url,
		bytes.NewBuffer([]byte(`{"name": "`+name+`"}`)),
	)
	// etc
}
```

次に、メソッドの抽出のリファクタリング（`command+option+m`）を使ってJSONペイロードの作成を関数に抽出し、メソッドからノイズを取り除きます。

```go
func (ws *WidgetService) CreateWidget(name string) error {
	url := ws.baseURL + "/widgets"
	req, err := http.NewRequest(
		http.MethodPost,
		url,
		createWidgetPayload(name),
	)
	// etc
}
```

パブリックなメソッドや関数は、*どのように*行うかではなく、*何を*行うかを説明するべきです。

> **コードが何をしているのかを理解するために考えなければならないときはいつも、その理解がよりすぐに明らかになるようにコードをリファクタリングできないか自問します**

-- Martin Fowler

これにより、全体的な設計をよりよく理解できるようになり、責務について問いかけることができるようになります。

>  なぜこのメソッドはXをするのか？それはYに置くべきではないか？

> なぜこのメソッドはこんなに多くのタスクをこなすのか？これをどこか別の場所にまとめられないか？

プライベートな関数やメソッドは素晴らしいものです。重要でない「どのように」を「何を」に包み込んでくれます。

#### でも、これではどう動くのかわからなくなる！

他の関数やメソッドで構成された、より小さな関数やメソッドを好むこのリファクタリングに対するよくある反論は、コードがどう動くのかを理解するのが難しくなる、というものです。これに対する私の率直な返答はこうです。

> ツールを使ってコードベースを効果的にナビゲートする方法を学びましたか？

`CreateWidget`の _書き手_ として、私は意図的に、特定の文字列の作成がメソッドの語りにおける重要な登場人物になってほしくないと考えています。それは99%の場合、読み手にとって気が散る、無関係なノイズです。

しかし、誰かが本当に _気にする_ のであれば、`createWidgetPayload`の上で`command+b`（あるいはあなたの環境での「シンボルへ移動」）を押して…それを読めばよいのです。`command+left-arrow`を押せば、また元に戻れます。

### 値の作成を構築時に移す

メソッドでは、先ほどの`CreateWidget`メソッドの`url`のように、値を作成してそれを使う必要があることがよくあります。

```go
type WidgetService struct {
	baseURL string
	client  *http.Client
}

func NewWidgetService(baseURL string) *WidgetService {
	client := http.Client{
		Timeout: 10 * time.Second,
	}
	return &WidgetService{baseURL: baseURL, client: &client}
}

func (ws *WidgetService) CreateWidget(name string) error {
	url := ws.baseURL + "/widgets"
	req, err := http.NewRequest(
		http.MethodPost,
		url,
		createWidgetPayload(name),
	)
	// etc
}
```

ここで適用できるリファクタリングのテクニックは、**メソッドの引数に依存しない**値が作成されている場合に、代わりに型に _フィールド_ を作り、コンストラクタ関数の中でそれを計算するというものです。

```go
type WidgetService struct {
	client          *http.Client
	createWidgetURL string
}

func NewWidgetService(baseURL string) *WidgetService {
	client := http.Client{
		Timeout: 10 * time.Second,
	}
	return &WidgetService{
		createWidgetURL: baseURL + "/widgets",
		client:          &client,
	}
}

func (ws *WidgetService) CreateWidget(name string) error {
	req, err := http.NewRequest(
		http.MethodPost,
		ws.createWidgetURL,
		createWidgetPayload(name),
	)
	// etc
}
```

値の作成を構築時に移すことで、メソッドをシンプルにできます。

#### `CreateWidget`の比較

最初はこうでした。

```go
func (ws *WidgetService) CreateWidget(name string) error {
	url := ws.baseURL + "/widgets"
	payload := []byte(`{"name": "` + name + `"}`)
	req, err := http.NewRequest(
		http.MethodPost,
		url,
		bytes.NewBuffer(payload),
	)
	// etc
}

```

ほぼ完全に自動化されたツールで駆動したいくつかの基本的なリファクタリングによって、次のようになりました。

```go
func (ws *WidgetService) CreateWidget(name string) error {
	req, err := http.NewRequest(
		http.MethodPost,
		ws.createWidgetURL,
		createWidgetPayload(name),
	)
	// etc
}
```

これは小さな改善ですが、間違いなく読みやすくなっています。十分に練習していれば、この種の改善にはほとんど1分もかからないでしょう。そしてTDDをうまく適用していれば、何も壊していないことを保証するテストという安全網があります。こうした継続的な小さな改善は、コードベースの長期的な健全性にとって不可欠です。

### コメントを取り除くようにする

> 私たちが従っている経験則は、何かにコメントを付ける必要を感じたときはいつでも、代わりにメソッドを書くというものです。

-- Martin Fowler

ここでも、メソッドの抽出のリファクタリングが味方になってくれます。

## ルールの例外

コードの改善の中には、テストの変更が必要でルールに反するにもかかわらず、それでも私が喜んで「リファクタリング」に分類するものもあります。

簡単な例としては、`shift+F6`でパブリックなシンボル（メソッド、型、関数など）の名前を変更することが挙げられます。これはもちろん、プロダクションコードとテストコードの両方を変更します。

しかし、これは**自動化された安全な**変更なので、他の種類の*設計*変更で多くの人が陥るような、テストとプロダクションコードを壊し続ける悪循環に陥るリスクは最小限です。

そのため、IDEやエディターで安全に実行できる変更であれば、私は喜んでリファクタリングと呼びます。

## ツールを使ってリファクタリングを練習する

- こうした小さな変更を1つ行うたびに、ユニットテストを実行するべきです。私たちはコードをユニットテスト可能にするために時間を投資しており、数ミリ秒のフィードバックループはその大きな利点の1つです。活用しましょう！
- ソース管理に頼りましょう。アイデアを試すことに遠慮すべきではありません。満足できたらコミットし、そうでなければ元に戻しましょう。これは気軽で簡単で、大したことではないと感じられるべきです。
- ユニットテストとソース管理をうまく活用すればするほど、リファクタリングを*練習*するのが簡単になります。この規律をマスターすれば、信頼性が高く効果的なフィードバックループと安全網があるので、**設計スキルは急速に向上します**。
- 私のキャリアの中であまりにも頻繁に、リファクタリングする時間がないと不満を言う開発者の声を聞いてきました。残念ながら、彼らにとってリファクタリングにそれほど時間がかかるのは、規律を持って行っておらず、十分に練習していないからであることは明らかです。
- タイピングがボトルネックになることは決してありませんが、使っているエディターやIDEが何であれ、それを使って安全かつ素早くリファクタリングできるべきです。たとえば、ツールでキー操作1つで変数を抽出できなければ、手間がかかりリスクも高いので、あまりやらなくなってしまうでしょう。

## リファクタリングするのに許可を求めない

リファクタリングは仕事の中で頻繁に行われるべきもので、常にやっていることであるべきです。また、特に少しずつ頻繁に行っていれば、時間を浪費するものであるべきではありません。

リファクタリングをしなければ、内部品質は低下し、チームの生産能力は落ち、プレッシャーは増していきます。

Martin Fowlerには、もう1つ素晴らしい言葉があります。

> ただし、締め切りが目前に迫っているとき以外は、時間がないからといってリファクタリングを先延ばしにすべきではありません。いくつかのプロジェクトでの経験から、ひとしきりリファクタリングを行うと生産性が向上することがわかっています。十分な時間がないということは、たいていの場合、リファクタリングが必要であることの表れです。

## まとめ

これは網羅的なリストではなく、あくまで出発点です。プロになるには、Martin Fowlerの『リファクタリング』（第2版）を読みましょう。

十分に練習していれば、リファクタリングは非常に素早く安全に行えるはずなので、やらない言い訳はほとんどありません。リファクタリングを、日常的な仕事の一部になるまで身につけるべきスキルとしてではなく、他の誰かが下す決定だと見なしている人があまりにも多すぎます。

私たちは常に、コードを*模範的な*状態にしておくよう努めるべきです。

優れたリファクタリングは、理解しやすいコードにつながります。コードを理解できれば、より優れた設計を見つけやすくなります。巨大な関数、不必要に重複したコード、深いネストなどがあるシステムでは、設計を見いだすのははるかに困難です。**より良い設計のためには、頻繁で小さなリファクタリングが必要です**。
